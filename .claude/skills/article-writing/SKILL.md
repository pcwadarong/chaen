# Article-Writing

chaen 블로그에 올릴 기술 아티클 **초안(마크다운)**을 쓴다. 블로그 글은 DB에 저장되고 마크다운 에디터로 입력하므로, 산출물은 **레포에 커밋하는 파일이 아니라 붙여넣을 마크다운**이다. 초안은 `docs/pr/{slug}-article.md`(gitignore 영역)에 두고 사용자가 에디터에 붙여넣는다.

> **문체·구조의 단일 출처는 기존 발행 글이다.** 이 스킬은 규칙을 새로 만들지 않고, 아래 글들의 결을 따른다:
>
> - `https://chaen.vercel.app/ko/articles/blender-three-js-character-issue` (기준 예시)
> - 그 외 `https://chaen.vercel.app/ko/articles` 의 최근 글 1~2개를 먼저 읽어 톤을 맞춘다(WebFetch).

## Step 1: 글 유형과 범위 확정

먼저 **어떤 결의 글인지** 사용자와 맞춘다. 범위(어떤 작업/PR을 묶을지)가 서사를 정하므로 애매하면 `AskUserQuestion`으로 확인한다.

| 유형          | 언제                       | 서사 골격                                             |
| ------------- | -------------------------- | ----------------------------------------------------- |
| 디버깅 스토리 | 버그를 파고들어 고친 작업  | 증상 → 가설 → 계측으로 반증 → 진짜 원인 → 수정 → 교훈 |
| 회고          | 하나의 기능/도입을 마친 뒤 | 배경 → 시도와 삽질 → 해결 → 구조적 교훈               |
| 개념 설명     | 배경지식이 필요한 주제     | 전제 → 그림 → 왜 이렇게 하나 → 함정                   |

여러 PR을 묶을 땐 **하나의 실로 꿰이는지** 먼저 본다(예: "렌더 루프" 3부작). 안 꿰이면 범위를 좁힌다.

## Step 2: 문체 규칙 (기존 글 준수)

| 항목      | 규칙                                                                                                      |
| --------- | --------------------------------------------------------------------------------------------------------- |
| 어투      | **존댓말 습니다체 + 회고 톤.** "헤매게 만듭니다", "확인하지 않았습니다", 감정 노출("찝찝함이 남았습니다") |
| 제목      | 문제 중심 + `— 회고`/`— N부작` 꼴. 명사형 종결 (예: "…망가졌다 — 3D 캐릭터 구현 회고")                    |
| 소제목    | **질문형**을 섞는다 ("왜 아래 씬이 돌지?", "멈춘 줄 알았는데?")                                           |
| 문단      | 3~7줄. 한 문단 = 한 생각                                                                                  |
| 독자 호명 | "개발자 팁 —", "번외 —" 블록으로 곁가지·함정을 분리                                                       |
| 결말      | 마지막에 **교훈을 추상화**한다 (예: "모델링 문제가 아니라 구조 설계 문제다")                              |

## Step 3: 구조 템플릿

```
# 제목 (문제 중심 + — 회고/N부작)

> TL;DR  (3줄 — 무엇을/왜/교훈)

도입 한 문단 — 이 글이 다루는 문제와 "왜 어려웠나"

## 들어가기 전에 — {개념}이 뭔가요?   ← 전제부터 깐다(용어·구조·좌표계)
   그림/다이어그램 + 이 글의 핵심 질문 한 줄

## 본론 (유형별 골격, 시간순)
   ### 발견 → ### 추적/가설 → ### 진짜 원인 → ### 처방
   > 버린 대안 / 개발자 팁 / 번외(함정) 블록

## 관통하는 교훈  (번호 매긴 3~4개)

## 한 장 요약  (전체 흐름 다이어그램 하나)
```

**밀도 원칙** (사용자 전역 문서 규칙과 동일):

- 전제부터 깐다 — 용어·구조를 건너뛰지 않는다.
- 그림을 아끼지 않는다 — ASCII 다이어그램·격자·화살표. **전/후는 반드시 나란히**.
- 실제 코드를 인용한다 — 요약 의사코드 말고 그 레포의 진짜 코드, 상수는 실제 값.
- 숫자는 표로. 측정이면 측정 조건(디스플레이 주사율 등)도 같이.
- **왜 다른 선택을 안 했는지** 쓴다.
- 함정은 인용블록·콜아웃으로 눈에 띄게.

## Step 4: 시각 자료

기존 글은 이미지 10~15개를 쓴다. 세 종류를 섞는다.

1. **ASCII 다이어그램** — 구조·타임라인·비교. 마크다운 코드블록으로 그대로 둔다.
2. **before/after 쌍** — 좌우로 나란히. 라벨(`before`/`after`)을 붙인다.
3. **실제 캡처** — 프로파일러·카운터·로그. 성능/타이밍 버그면 **직접 계측 캡처를 만든다**.

계측 캡처가 필요하면 → **[references/capture-workflow.md](./references/capture-workflow.md)** 절차를 따른다(before/after 빌드 + GPU 브라우저 HUD 오버레이 + 스크린샷). 함정: headless 소프트웨어 렌더링(≈4fps)은 프레임레이트를 뭉개므로 **GPU 활성 브라우저**에서 찍는다.

본문엔 `> 🖼️ **[캡처 N: 설명]**` 자리표시자를 두고, 맨 아래에 **이미지 체크리스트**로 무엇을 넣을지 정리한다.

## Step 5: 저장·전달

- 초안은 `docs/pr/{slug}-article.md`에 쓴다(gitignore라 커밋 안 됨 — 붙여넣을 원고).
- 블로그 아티클은 DB 저장이므로 **레포에 커밋하지 않는다.** 마크다운 에디터에 붙여넣는 게 게시 방법이다.
- 실제 코드·상수·수치는 **쓰기 직전에 파일을 다시 열어 확인**한다(기억으로 쓰면 상수·함수명이 틀린다).
